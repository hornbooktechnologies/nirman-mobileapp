## Verification and remaining acceptance

- Full Web type-check, lint and production build passed after removing the unused `ResponsiveFilterBar` export/component and correcting three test-harness variable names. All 119 Web `.test.mjs` behavior tests passed with Node test isolation disabled in this Windows sandbox. `git diff --check` passed. No API, database, Mobile, dependency or production business data was changed for Phase 9.
- Source check: the shared drawer uses a native modal dialog, restores focus, locks background scroll, handles Escape and keeps a scrollable content region; shared inputs/buttons expose focus indicators and reduced-motion styles. These properties still need keyboard and screen-reader observation in a browser.
- Follow-up browser pass: an approved local Web dev server ran on port 3001 with its API rewrite pointed at an unavailable localhost API, so no deployed business data was touched. Synthetic phase 2–8 previews rendered headings without Next error overlays or page-level horizontal overflow at 1366×768, 768×900, 683×384 and 360×740 CSS viewports. The 683×384 check approximates 1366×768 at 200% reflow; it is **not** native browser zoom. Visual spot checks covered Worker, Wages/Kharchi, Sales and Administration layouts. Administration's synthetic filter fixture was corrected so its displayed records follow the applied status/search; browser checks confirmed draft cancel with Escape, focus restoration, Shift+Tab boundary wrap, Apply, Reset and filtered-empty state. Worker read-only and Dashboard restricted/archived synthetic states responded as expected. The signed-out `/dashboard` route redirected to `/login`; `/forgot-password` opened from Login. Browser errors were empty; Next logged a nonblocking logo aspect-ratio warning, although the rendered image retained its intrinsic ratio. Server logs showed expected `ECONNREFUSED` refresh attempts against the deliberately unavailable local API. The test tab and dev server were closed afterward.
- Still unrun: actual 200% browser zoom, complete keyboard-only and reduced-motion walkthroughs, all production-route long/populated/empty/error/stale states, signed-in Builder/Contractor/Supervisor/Sales and CUSTOM/read-only journeys, list/detail/back restoration with real records, effective-role and organization/project isolation with authorized accounts, cross-client behavior, and runtime mutation/recovery checks. The local API was deliberately unavailable and no authorized non-production test sessions were provided during this pass. Source/tests and synthetic fixtures do not establish those results.
- Contract limits remain: no server search/pagination contract for several administration lists; no supported worker filter for project-wide Wages. Kharchi already supports `workerId`, and the Worker Detail link now supplies it. There is no exact progress-update-to-gallery-photo relationship, and some dashboard organization-wide aggregates are unavailable. Do not fill these with derived or sample values.

The follow-up API source check narrowed those limits: `organizations` and organization `members`, platform `roles`, and subscription `plans` currently return unfiltered collections; `users` already accepts server search/role/page and Kharchi already accepts `workerId`/`workerAssignmentId`. Wages `preview` accepts a period and `batches` returns the project's batches without a worker query. Progress history and Gallery entries expose separate project-scoped resources without a progress-update/photo relationship. The Dashboard endpoint is scoped to one organization and project, so it cannot by itself supply organization-wide totals. Any new server query, relationship or aggregate needs its own contract and permission review before Web consumes it.

Phase 9 is implemented and statically verified, with synthetic browser reflow/interactions verified. Production browser and role acceptance remain pending. No later phase is started.
